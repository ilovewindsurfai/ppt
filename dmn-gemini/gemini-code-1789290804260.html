Focus Architecture : Analyse du mode Batch (S3 / JSONLines) pour Spring Boot Kogito

Auteur : Équipe Data & Architecture

Date : Septembre 2026

Statut : En révision / Arbitrage

Projet : Moteur de Règles & Traitement Volumétrique (80 Millions de lignes)

1. Contexte & Problématique

Dans le cadre de l'implémentation des règles métier DMN, l'équipe d'architecture propose l'utilisation du framework Spring Boot Kogito. Afin de répondre au besoin de traitement volumétrique (lot de 80 millions de lignes), la cinématique envisagée consiste à faire transiter les données via AWS S3 sous forme de fichiers jsonlines compressés en .zip.

L'objectif de ce document est d'évaluer la pertinence technique, opérationnelle et financière de ce choix face aux capacités natives du cluster Databricks / Delta Lake.

2. Description de la Cinématique Envisagée

+-----------------+ Écriture ZIP +-----------+ Lecture & Unzip +---------------------+ | |------------------------->| |---------------------------->| | | DATABRICKS | | AWS S3 | | SPRING BOOT KOGITO | | (Data Lake) |<-------------------------| (Storage) |<----------------------------| (Calcul DMN) | +-----------------+ Lecture Audit +-----------+ Écriture Audit +---------------------+
  1. Extraction : Databricks génère et dépose un fichier jsonlines géant de 80M de lignes compressé (.zip) sur un bucket AWS S3.
  2. Traitement : L'application applicative Spring Boot Kogito télécharge le fichier, le décompresse, exécute le moteur DMN et génère la structure d'audit (résultats des sous-décisions et règles matchées).
  3. Restitution : Spring Boot réécrit les résultats enrichis de l'audit sous forme de fichier JSON sur AWS S3, relu ultérieurement par les pipelines Databricks.

3. Analyse d'Impact & Matrice des Risques

L'analyse technique met en évidence un décalage entre l'outil applicatif utilisé et la nature du besoin (Big Data Batch).

Axe d'analyse Constat & Impact technique Niveau de risque
Volumétrie & Mémoire 80M de lignes d'audit représentent 15 à 40 Go de JSON uncompressed. Risque majeur de saturation de la Heap JVM (OutOfMemoryError) sur Spring Boot lors de la sérialisation/désérialisation. ÉLEVÉ
Parallélisme & Scalabilité Le format ZIP impose un dépilement séquentiel. On annule la capacité de calcul distribué de Databricks en transférant le traitement lourd à un runtime applicatif mono-instance. ÉLEVÉ
Résilience & Operations Absence de checkpointing natif dans Spring Boot. En cas de crash à la 75ème millionième ligne, l'intégralité du traitement batch doit être rejouée depuis le début. ÉLEVÉ
Complexité de Développement Obligation de développer au sein de Spring Boot une logique « fait maison » de multithreading / chunking pour absorber le volume, recodant ce que Spark fait nativement. MOYEN
Coût d'Infrastructure Inefficience financière : sous-utilisation des nœuds Databricks en attente + surdimensionnement obligatoire des instances Spring Boot (CPU/RAM) pour les pics batch. MOYEN

4. Étude Comparative des Alternatives

Critère Option 1 : Pure SQL Databricks Option 2 : Spring Boot Kogito (via S3) Option 3 : Lib DMN Native dans Spark
Lieu d'exécution Cluster Databricks Serveur Spring Boot externe Cluster Databricks (Executors)
Throughput / Débit Ultra-rapide (Vectorisé Parquet) Faible à Moyen (Bridé par le JSON) Excellent (In-Memory Spark)
Finesse d'audit Décision finale uniquement Sous-décisions + Matched Rules Sous-décisions + Matched Rules
Traçabilité Native (Delta Lake Time Travel) Fichier JSON d'audit sur S3 Native (Delta Lake Struct/JSON)
Complexité Infra Minimale (0 composant de plus) Élevée (Cluster App + Monitoring) Faible (Dépendance JAR Java/Scala)

5. Recommandations & Arbitrage

Synthèse de l'évaluation :
Le transfert de S3 à S3 résout la bande passante réseau, mais l'utilisation de Spring Boot Kogito comme moteur de traitement Batch reste un anti-pattern d'architecture Big Data.

Pistes d'arbitrage proposées :

  1. Si l'audit détaillé des tables intermédiaires N'EST PAS réglementaire :
    ➡️ Recommandation : Basculer sur l'Option 1 (Databricks SQL Natif). C'est la solution la plus performante, la moins chère et la plus simple à maintenir. L'auditabilité globale est assurée par le versioning Delta Lake Time Travel et les commits Git des règles.

  2. Si l'audit détaillé de chaque sous-table de décision EST obligatoire :
    ➡️ Recommandation : Implémenter l'Option 3 (Moteur DMN embarqué sous forme d'UDF / librairie Java native dans Spark). Cette approche conserve 100 % de la finesse d'audit DMN de Kogito (via la même librairie kie-dmn-core), tout en exécutant le calcul de manière distribuée et native au sein de Databricks.
